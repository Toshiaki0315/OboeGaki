# 性能計測の記録（spec §6.6）

基準は参照実装から引き継ぐ（CLAUDE.md §7）。**検証していない性能を
「できました」と報告しない**ためのそろばん。

| 指標                  | 基準                    | 実測（2026-09-04, Apple Silicon）                                                                                                                                                               | 判定             |
| --------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| キー入力 → 画面反映   | p95 < 16ms（10,000 語） | dispatch p50 = 3〜4ms / **p95 = 10.5〜14.9ms（3 回計測）** / max = 30.3ms（83KB・13,523 語・7,023 行・表 260 + 数式 260 + :::note 260 の意地悪文書、300 打鍵。2026-09-04 に全機能込みで再計測） | **合格**（注 1） |
| 全文検索              | < 200ms（5,000 ノート） | 最悪 **2ms**（trigram 多数ヒット。希少ヒット・ヒットなし・LIKE 2 文字はすべて ≤ 2ms）                                                                                                           | **合格**         |
| 起動 → ウィンドウ表示 | < 1.5 秒                | **903ms**（release ビルド、プロセス開始 → React マウント）                                                                                                                                      | **合格**         |

付随の実測:

- 索引の初回構築（5,000 ノート）: 2.2 秒 — vault を最初に開くとき 1 回だけ。
  **現状は vault_open 内で同期実行**なので、大きな vault では体感される。
  背景化（spec §7.3「走査は QThreadPool」相当の Tauri 非同期化）は今後の課題
- 再同期（変更なし・5,000 ノート）: 25ms — 開き直しごとのコストとして許容圏

## 測り方

- **検索**: `make bench-search`（= `cargo run --release --bin bench`）。
  一時フォルダに 5,000 ノートを生成 → 索引構築 → 4 種のクエリを計測。
  基準割れで exit 1
- **打鍵**: `npx vite` を起動して `http://localhost:5183/bench.html` を開く
  （自動実行、結果は画面と `window.benchResult`）。本番と同じ拡張一式の
  EditorView に 300 打鍵を注入する
- **起動**: `make bench-startup`。release を組み、`OBOEGAKI_BENCH_STARTUP=1`
  で起動すると「プロセス開始 → React マウント」を印字して終了する

## 注意（注 1）

- 打鍵の主計測は **dispatch（CM6 の同期 DOM 更新）まで**。描画（paint）は
  ページが可視のときだけ別途採れる（非表示ページは rAF が止まる）。
  小さな差分の paint は GPU 側で軽いが、厳密には WKWebView の実機で
  可視状態の計測を採るのが望ましい
- 発見と対処: 表が多い文書で p95 が 17.7ms に割れた → tableField を
  「表の近くに触れた編集・リビール変化のときだけ再計算、それ以外は
  位置写像で使い回す」に最適化して 13.9ms（回帰テストあり）
- 発見と対処（2026-09-03、第 2 群）: 見出し折りたたみの導入直後に p95 が
  26.5ms に割れた。原因は foldService が呼ぶ headingSection の
  `tree.iterate` — enter で false を返しても走査は止まらず、可視の
  見出しごとに文書末まで舐めていた。トップレベルの兄弟歩きに替えて
  5.6ms。ベンチ自体も本番と同じ拡張一式（codeLanguages・front matter・
  折りたたみ・オートペア込み）で測るよう更新した
- 発見と対処（2026-09-04、レビュー）: 数式・図・:::note の blockWidgetField が
  毎打鍵・毎カーソル移動で全再計算（noteContainers の全行走査 × 2 +
  全数式の Temml 組み直し）しており p95 17〜25ms に割れていた。対処は
  ① 解析の進みを木の同一性でなく届いた位置（tree.length）で判定
  ② blockWidgetField に表と同じ間引き（ゾーン + 位置写像 + リビール鍵）
  ③ renderMath の結果キャッシュ ④ noteContainers の行頭 : 速攻棄却と
  1 パス化。計測文書に数式・:::note も追加（測っていない経路で合格を
  名乗らない）。実測 p95 = 10.5 / 14.9 / 13.8ms（3 回とも合格）
- JS のオフセットは UTF-16。文書はすべて BMP 内
