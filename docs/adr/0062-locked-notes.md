# ADR-0062: パスワードで施錠するノート（暗号化）

- 状態: **検討中（実装しない）**。決めることが 3 つ残っている（末尾）
- 日付: 2026-09-12
- 関連: ADR-0023（履歴は作り直せない）、ADR-0051（MCP）、T1 / T7

## 背景

「暗号化とパスワードが必要なプライベートメモは作れるか」という問い
（2026-09-12）。暗号そのものは Rust の crate で数十行で、難しくない。
**難しいのは周りの全部** — このアプリは平文を前提に速さと便利さを組んで
あり、平文は `.md` 以外に 3 か所へ散っている。

| 場所                        | 今                                                          | 暗号化すると                                                |
| --------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 索引 `index.sqlite`         | `notes_fts` に**本文まるごと**、`notes.preview` に冒頭 200 字 | 入れたら暗号化の意味が消える → **全文検索できない**         |
| 履歴 `.OboeGaki/history/`   | 版を平文 `.md` で保存。**作り直せない**（ADR-0023）           | 版も暗号化するか、残さないか。鍵を失えば版ごと読めない      |
| 退避（クラッシュ復元）      | 平文で書き出す                                                | 同じ手当てが要る                                            |
| 一覧のプレビュー            | 索引の平文から出す                                            | 施錠中は 🔒 だけ                                             |
| 添付（画像・PDF）           | `attachments/` に素で置く                                     | **本文を隠しても画像は丸見え**                              |
| MCP（ADR-0051）             | `.md` を読む                                                  | 施錠中は断る（`.mcp-ignore` と同じ道に乗る）                |

追い風もある。**読み書きの境目に変換を挟む前例が既にある** — Shift_JIS の
ノートは `vault::decode_text` が読むときに変換し、保存は UTF-8 で書き戻る。
暗号も同じ位置（`vault::read_note` / `autosave::save_atomic`）に挟めるので、
エディタ側（T1・CM6）は**一切触らずに済む**。

## 案（最小形）

「施錠付きノート」を**別の種類**として持つ。

- 拡張子を分ける（`.md.enc`）。`vault::scan()` が拾わないので、索引・検索・
  やること・リンク・MCP から**自動的に外れる**（除外を書き足さなくて済む）
- 中身は XChaCha20-Poly1305、鍵は Argon2id でパスワードから作る。ファイルの
  頭に salt と nonce と版を置く
- 開くときだけパスワードを聞き、**開いている間だけ**平文がメモリにある。
  一定時間で自動施錠。鍵はメモリの外に出さない
- 履歴は**残さない**（残すなら同じ鍵で暗号化する。どちらにせよ「鍵を忘れたら
  終わり」は変わらない）
- 添付は**対象外とはっきり言う**（隠したい画像は貼らない）

### 失うもの（施錠したノートでは効かない）

検索・プレビュー・履歴・やること一覧・バックリンク・Claude 連携。
つまりこのアプリの便利さの大半。**めったに開かない、本当に見せたくない
数枚**のための機能で、常用するノートには向かない。

### 却下した案

| 案                                       | 問題                                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------- |
| 保管フォルダごと暗号化                   | macOS の FileVault と仕事が重なる。アプリが持つ理由が薄い                 |
| 索引も暗号化して検索できるようにする     | **別物**。暗号化索引の設計になり、この規模では割に合わない                |
| front matter に `locked: true` で同じ拡張子 | 平文と同じ道を通るので、索引・履歴・MCP の除外を**全部手で**書くことになる |

## 守れないもの（はっきり書く）

- 動いている間の**メモリ上の平文**（WebView が持つ）。ここは守れない
- 施錠中でも**ファイルの大きさと更新時刻**は見える
- macOS のスワップ・メモリダンプ
- **鍵を忘れたら読めない**（復旧手段は作らない）

盗難・押収まで想定するなら FileVault が本筋で、この機能は**その上乗せ**に
すぎない。狙いは「席を外した隙に、同じ Mac を使う人に読まれない」こと。

## 決めること（ここが決まるまで実装しない）

1. **鍵の単位** — ノートごとにパスワード（強いが毎回聞かれる）か、保管
   フォルダに 1 つ（楽だが全部同じ鍵）か
2. **守りたい相手** — 席を外した隙か、盗難・押収までか（後者なら FileVault
   の案内が先）
3. **鍵を忘れたら諦める**でよいか（復旧手段を作らない）

## 見積もり

- 暗号の芯（鍵導出・封入・開封・ファイル形式）: **半日**。純 Rust でテストも楽
- 周り（施錠・解錠の窓、一覧での見え方、自動施錠、パスワード変更、索引と
  履歴からの除外、MCP の拒否、手引き、手動チェック）: **数日**
