# ADR-0050: パスの文字列は vault からの相対部分を NFC に揃える

- 状態: 採用
- 日付: 2026-09-09

## 背景

実機で、テキストエディタ（Cocoa アプリ）でノートを書き換えたら、一覧に同じ
ノートが 2 行並んだ。Finder には 1 つしか無い。索引を見ると、同じファイルが
**NFC と NFD の 2 つのパス文字列**で入っていた。

- macOS のファイルシステム（APFS / HFS+）は正規化の違いを**同じ名前**として
  扱う。「プ」（U+30D7）と「フ + 半濁点」（U+30D5 U+309A）で同じファイルが
  開ける
- しかし文字列としては別物。Cocoa の `fileSystemRepresentation` は NFD を
  作るので、Cocoa アプリはファイルを NFD のパスで書く。FSEvents はその
  **書き手が使った字面**で届ける
- アプリ自身は NFC で作る・書く。走査（`read_dir`）はディスクの字面を返す
- 監視イベントの NFD パスでそのまま `upsert` したため、索引のキーが二重に
  なった。フロントも `change.path !== currentPath` で「別のノート」と見て、
  開いているノートを読み直さなかった

濁点・半濁点のある仮名（が・ジ・プ…）は日本語の題名にふつうに出てくる。
日本語のノートアプリとしては避けて通れない。

## 決定

**パスが文字列になる境目で、vault からの相対部分を NFC に揃える**
（`vault::nfc_under`）。

- 走査（`Vault::scan`）が返すパス
- 索引のキー（`index_db::key_of` — `index_one` / `sync` / `remove`）
- 監視イベントでフロントへ届けるパス（`watcher::event_path`）
- 無視リスト（`Suppressor`）の比較は丸ごと NFC の字面で行う

root そのものは触らない（フロントが持っている root の字面と揃えるため。
相対部分だけを直す）。NFC のパスでディスクを読む・書くのは、正規化を区別
しないファイルシステムの上では問題ない。

`wikilink::normalize` と `vault` の題名比較が既に NFC を使っている
（レビュー 2026-09-04）。今回はそれを**パスにも広げた**形。

## 影響

- 索引に残っていた NFD の行は、次に vault を開いたときの `sync` が
  「走査に無いキー」として消す（走査は NFC で返るようになったため）
- `related_signals` などが返す鍵も NFC になる（テストの期待を直した）
- Linux（ext4 は正規化を区別する）で NFD の名前のファイルがあると、NFC の
  パスでは開けなくなる。このアプリは macOS 13+ 専用（spec §1）なので受け
  入れる。持ち出すときはここを見直す
