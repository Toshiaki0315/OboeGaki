# ADR-0038: 印刷は「書き出しと同じ本文」を隠しの領域に組んで刷る

- **日付**: 2026-09-04
- **状態**: 採用
- **覆す対象**: ADR-0007 の「PDF は生成した HTML を `QTextDocument.setHtml()`
  に渡す」という**実現手段**（Qt 固有）。「HTML と PDF は同じ文字列を使う。
  経路を分けると片方だけ直す事故が起きる」という**判断は引き継ぐ**

## 背景

Qt 版の PDF は `QTextDocument.setHtml()` に流していた。Qt のリッチテキストは
CSS の一部（`border-left` など）を解さないので、引用の縦線は PDF に出ない
——ADR-0007 はそれを承知で選んでいた。

Tauri 版に `QTextDocument` は無い。macOS の WebView（WKWebView）には
**印刷パネルがある**（wry の `print()` が `printOperationWithPrintInfo:` を
呼ぶ。ここから「PDF として保存」も選べる）ので、Qt が解さなかった CSS も
そのまま紙に出る。専用の PDF 書き出しを別に作る理由が無い。

問題は**何を刷るか**。この印刷は「今この WebView に出ているもの」を刷る。
アプリの画面をそのまま刷ると:

- サイドバーもステータスバーも一緒に刷られる
- **本文が欠ける。** CM6 は見えている範囲＋前後だけを DOM に持つ
  （仮想スクロール）ので、長いノートは画面に出ていない部分が紙にも出ない

## 決定

1. **書き出しと同じ本文**（`renderBody`）を、隠しの `.print-root` に組んでから
   刷る。図（Mermaid の SVG）も画像（data URL）も書き出しと同じ経路で埋める
2. `@media print` で `.app` を消し、`.print-root` だけを紙に出す
3. **組み終わって画面に出てから**印刷パネルを出す（`requestAnimationFrame`
   を 1 つ挟む）。先に呼ぶと、まだ DOM に無いものが刷られる
4. 刷った本文は**消さずに残す。** 印刷パネルは非同期に開くので、閉じる前に
   中身を消すと途中で紙が空になる。次に刷るときとノートを閉じたときに入れ替える
5. 印刷用の CSS は書き出しの STYLE と**別に持つ**（あちらは書き出した
   ファイルの `body` に効く。こちらはアプリの中の `.print-root` に効く）。
   見た目は対で保つ

## 根拠

| 案 | 内容 | 問題 |
| --- | --- | --- |
| A | アプリの画面をそのまま刷る | **本文が欠ける**（CM6 の仮想スクロール）。サイドバーも出る |
| B | 別の窓に書き出し HTML を読ませて刷る | 窓とファイル URL の許可が要る。刷るためだけに窓が増える |
| C | **隠しの領域に書き出しと同じ本文を組んで刷る** | 印刷用の CSS を 1 枚持つ |
| D | 書き出した HTML をブラウザで開いて刷ってもらう | アプリの機能として成立していない |

C は**書き出しと同じ関数で本文を作る**ので、ADR-0007 の「経路を分けない」を
守れる。iframe（B の変種）は**中身がページ送りされず 1 ページで切れる**ので
採らない。

## 影響

- `Cmd+P` で macOS の印刷パネルが出る。「PDF として保存」もそこから
- 専用の PDF 書き出しは作らない（メニューが 1 つ減る）
- 印刷の見た目（改ページの位置・余白）は**実機でしか確かめられない**。
  手動チェックに項目を足した
- `export-html.ts` に `renderBody` が増えた（`renderHtml` はそれを包む）
