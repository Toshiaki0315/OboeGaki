# ADR-0063: ノートを Qiita へ投稿する

- 状態: 採用（2026-10-02。決めること 4 つを末尾の「決定」に記した。実装は TASKS 第 14 群）
- 日付: 2026-09-12
- 関連: ADR-0005（題名は本文の見出し）、ADR-0046 決定 4（文書ごとの覚え書きは
  front matter）、ADR-0052（保管フォルダは共有されうる）

## 背景

「ノートを Qiita に流し込む仕組みは作れるか」という問い（2026-09-12）。
**土台はほぼ揃っている** — 暗号化（ADR-0062）とは逆に、既にあるものを
壊さずに載る。

追い風:

- **記法がもともと Qiita 寄り**。`:::note` / `:::details`、コードフェンスの
  ファイル名ラベル（` ```ruby:app.rb `）は Qiita に合わせて入れた（第 6 群）
- **題名は本文の H1**（ADR-0005）= Qiita の `title` にそのまま渡せる
- **文書ごとの覚え書きの置き場が既にある**（front matter。ADR-0046 決定 4）。
  記事 ID をここに残せば、`.md` を Finder で移しても付いて回る
- API は素直: `POST /api/v2/items` で新規、`PATCH /api/v2/items/:id` で更新。
  認証は個人用アクセストークン 1 本（`write_qiita`）

## 引っかかるところ

| 事柄                     | 中身                                                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **画像**                 | **ここが最大の穴。** Qiita API に画像アップロードの口が無い。`attachments/図.png` のリンクは切れる                                 |
| **トークンの置き場**     | `.md` にも `.OboeGaki/` にも置けない（保管フォルダは共有・同期されうる = ADR-0052）。macOS の Keychain に入れる                   |
| **外に出る通信が初めて** | 今の通信は Ollama（localhost）だけで、しかも `TcpStream` の手書き HTTP（llm.rs）。TLS が要るので HTTP クライアントを 1 つ足す     |
| **トークンを WebView に渡さない** | 叩くのは Rust 側。TS には結果だけ返す                                                                                    |
| **タグ**                 | Qiita は 1〜5 個必須。本文の `#タグ` を流用するか、front matter に別に書くか（決めること 1）                                      |
| **向こうで編集されたら** | こちらの更新が上書きする。`updated_at` を覚えて食い違ったら止める                                                                 |

## 案（最小形）

1. 環境設定「Qiita」タブでトークンを 1 度だけ入れる（**Keychain へ**。
   保管フォルダにも設定 JSON にも書かない）
2. 「ファイル」→「Qiita に投稿…」でタグを確かめる小窓 → 投稿
3. **初回は必ず「限定共有」（`private: true`）で出す。** 読み返してから、
   公開はブラウザで押す — **外に出す操作をアプリ側で完了させない**
4. 成功したら front matter に `qiita: <item_id>` を書き戻し、次からは同じ
   記事を更新する（**アプリから front matter を書く数少ない例**。ピン留めと
   同じ扱い＝ユーザーの明示操作の結果としてだけ書く）
5. 送る前に本文から front matter と先頭の H1 を外す（H1 は title として渡す）
6. 画像リンクが残っていたら、投稿前に「この 3 枚は Qiita に載りません」と
   **先に言う**（黙って壊れたリンクを出さない）

### 却下した案

| 案                                       | 問題                                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ |
| 公式の `qiita-cli` に任せる              | 自分専用のフォルダで記事を管理する作り。保管フォルダと**二重管理**になる                   |
| 画像を自動でどこかに上げる               | 置き場（外部サービス）を持たせることになる。**おぼえがきの守備範囲を超える**                |
| Qiita から取り込む（双方向）             | 別の話。まず片道で足りるか見てから                                                          |
| トークンを front matter や設定 JSON に置く | 保管フォルダは共有・同期されうる（ADR-0052）。秘密を `.md` の側に置かない                  |

## 決めること（ここが決まるまで実装しない）

1. **タグの決め方** — 本文の `#タグ` を使う / front matter に `qiita-tags:` を
   別に書く / 投稿のたびに窓で選ぶ
2. **公開の既定** — 限定共有で出して手で公開（推奨）/ 最初から公開
3. **画像** — 警告するだけでよいか（自動で外部に上げる道は作らない）

## 見積もり

- 芯（トークン・投稿・更新・front matter の往復）: **1 日ほど**
- 周り（設定タブ、確認の小窓、画像の警告、手引き、手動チェック）: **2〜3 日**

暗号化（ADR-0062）と違い、**既存の仕組みを壊さない**（索引も履歴も検索も
そのまま）。

## 実装前に確かめること

Qiita API v2 の仕様は**着手時に公式ドキュメントで確かめ直す**
（この ADR は 2026-09-12 時点の理解で書いている）。とくに画像アップロードの
口が本当に無いか、レート制限、タグの文字種。

## 決定（2026-10-02）

1. **タグは本文の `#タグ` を初期値にする。** 投稿の小窓に並べ、そこで足し引きして送る
   （1〜5 個）。front matter にタグは書かない — タグ付けを二重に管理しない。
   **更新のとき**は小窓に Qiita 側の今のタグではなく本文の `#タグ` を出す（本文が真実）
2. **新規は必ず限定共有（`private: true`）で出す。** 公開は Qiita の画面で押す —
   外に出す操作をアプリ側で完了させない。**更新では `private` を送らない**
   （公開済みの記事を限定共有に戻そうとして失敗する・あるいは引っ込めることを避ける。
   公開の状態は Qiita 側が持つ）
3. **画像は投稿前に警告し、そのまま送れる。** 保管フォルダの中の画像（`attachments/` など
   相対パス）を数えて「この N 枚は Qiita に載りません」と出す。送るとリンクは切れたまま
   （Qiita の画面で貼り直す）。`https://` の画像はそのまま載るので数えない。
   外部へ自動で上げる道は作らない
4. **（追加）おぼえがき独自の記法は素の文字に直して送る。**
   `[[設計|手引き]]` → `手引き`、`[[設計]]` → `設計`、`::大事::` → `大事`、
   `:::center` / `:::right` の囲みは外して中身だけ、文字色の `<span style>` は外して
   中身だけ。`![[ノート]]`（埋め込み）は HTML 書き出しと同じく展開する。
   数式・Mermaid・`:::note` / `:::details`・コードのファイル名ラベルは Qiita も
   読めるのでそのまま。**コードの中は触らない**

### API の確かめ直し（2026-10-02。公式ドキュメント https://qiita.com/api/v2/docs）

- 作成 `POST /api/v2/items`: `title`・`body`・`tags`（`[{name, versions}]`）が必須。
  `private` で限定共有。201 で記事（`id`・`url`・`updated_at`）が返る
- 更新 `PATCH /api/v2/items/:item_id`: `title`・`body` が必須、`tags`・`private` は任意。200
- 認証は `Authorization: Bearer <token>`、投稿には `write_qiita` スコープが要る
- **画像アップロードの口は無い**（利用者情報に `image_monthly_upload_limit` があるだけ）
- レート制限: 認証ありで 1 時間に 1,000 回。エラーは `{message, type}`、状態は
  400 / 401 / 403 / 404 / 429 / 500
- 文書に**書いていない**こと: タグ 1〜5 個・タグの文字種・「公開した記事は限定共有に
  戻せない」は Qiita の画面側の決まりで、API 文書には無い。送る前に TS 側で 1〜5 個を
  確かめ、残りは API のエラー（message）をそのまま読める形で出す

## 追記（2026-10-05）: 本文の `#タグ` と、ファイルへの書き出し

要望: Qiita の本文に `#タグ` が字のまま残る。エクスポートで Qiita を選んだら
Qiita に合わせた形に変えてファイルに保存したい。

- **本文の `#タグ` は送らない**（投稿もファイルも同じ `qiitaDraft`）。タグは Qiita の
  タグとして渡すので、`#タグ` だけの行は行ごと外し、文中の `#Rust` は `#` だけ外して
  語を残す（語まで消すと文が欠ける）。決定 1 の「本文には残す」を覆す
- **「エクスポート」→「Qiita 用 Markdown…」を足す**（API での投稿も残す）。形は公式の
  qiita-cli の記事ファイル（front matter に title・tags・private・updated_at・id など。
  README の `npx qiita new` の雛形に揃えた）。却下した案「qiita-cli に任せる」は**記事の
  管理を任せる**ことを退けたもので、ファイルを渡すだけなら二重管理にならない
- `private` は常に `true`（決定 2）。投稿済みのノートは `id` と `updated_at` を入れ、
  qiita-cli で同じ記事の更新にする（向こうで編集されていれば qiita-cli が断る）。
  公開済みの記事を qiita-cli で更新するときは、使う人が `private: false` に直す
